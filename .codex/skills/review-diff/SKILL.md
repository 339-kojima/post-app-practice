# PR 差分レビュー

依頼者が指定した PR の差分を、設計資料・既存仕様・実装の観点から確認し、根拠のある指摘を報告する。レビュー依頼ではアプリケーションコードを変更しない。

## 手順

1. 対象リポジトリと PR 番号を確認し、`gh pr diff <番号>` で差分を取得する。接続に失敗した場合は環境の承認手順に従って再試行する。取得できなければその旨を伝え、手元にある情報だけで差分内容を断定しない。
2. 差分に含まれる設計書・仕様資料を読み、受け入れ条件や既存動作と照合する。設計に記載のない依存関係（例: `composer.json`）、設定変更、無関係なファイルの追加・編集にも注意する。ファイル名だけでなく、変更目的が説明されているか確認する。
3. 依頼者が指定した「触っていないはず」のファイルを順に確認する。まず削除行を調べ、次に追加・変更行が意図した仕様に必要か確認する。差分にないファイルも、その事実を明記する。
4. 変更内容を読み、依頼に応じて N+1、認可の置き場所と抜け道、マスアサインメント、Blade 等の出力エスケープ、CSRF、入力検証と日本語のエラー文、既存コードとの書き方の揃いを確認する。設計書とリポジトリ固有ルールも照合する。
5. 報告には差分上の根拠と行番号を付ける。PR の差分とローカルファイルが異なる場合があるため、対象ブランチや該当コミットの内容を確認し、行番号と参照先を取り違えない。

## 判定と報告

- 依頼者が判定語を指定したらそれを使う。指定がなければ「要確認」「OK」「対象外」を使う。確認材料が足りない場合は「要確認」とし、不足している情報を具体的に書く。
- 指定された列順・報告順・対象ファイルを守る。表形式を指定されていない場合、1観点につき1行で `観点 / 判定 / ファイル名:行番号 / 気づいたこと` の形式を使う。
- 不具合と断定できない設計外変更や一貫性の懸念は、確認できた事実と判断できない理由を分けて「要確認」とする。
- 依頼された場合、最後に人が自分の目で読むべき場所を優先順で最大3つ挙げる。
- 依頼されていないテスト実行、コード修正、PR への書き込みは行わない。
